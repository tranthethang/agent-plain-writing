# 日本語の例: ブログ(です・ます調)

例の中の出来事は、手本として作った話である。実際の作業では、筆者自身の体験を使う。

## Bad → Good

### 1. 書き出し

**Bad:** 技術が日々進化する現代において、状態管理はアプリ開発で非常に重要な役割を果たしています。それでは、一緒に見ていきましょう！
**Good:** 先週、Reactアプリのボタンが2秒遅れて反応しました。原因は、すべてのデータを1つのグローバルstateに入れていたことです。

### 2. 概念の説明

**Bad:** キャッシュとは、頻繁にアクセスされるデータのコピーを一時的に保存することで、データ取得の高速化を図るための仕組みです。
**Good:** キャッシュは、よく使うデータをあらかじめ保存しておいたコピーです。次に必要になったとき、計算し直さずに済みます。

### 3. 個人の意見

**Bad:** TypeScriptを導入することにより、開発プロセスにおいて多くのメリットが得られると言えるでしょう。
**Good:** TypeScriptに替えてから、型のミスを書いている最中にエディタが教えてくれるようになりました。実行して初めて気づくことがなくなりました。

### 4. 得た教訓の具体化

**Bad:** この経験を通じて、計画を立てることの重要性を改めて認識することができました。
**Good:** 学んだのは、コードを書く前に10分だけ計画を書くことです。これを省いて、半日を無駄にしました。

### 5. 漠然とした助言

**Bad:** コードの品質には常に注意を払い、プロジェクトの長期的な持続可能性を確保することが重要です。
**Good:** ルールを1つ決めます。テストが失敗している間は、マージしません。このルールに、先月3回助けられました。

### 6. 限界を認める

**Bad:** この方法には多少の課題がある可能性がございますが、概ね良好な結果が得られております。
**Good:** この方法は、通信が途中で切れた場合に対応できません。もっと簡単な方法は、まだ見つかっていません。

## 完成見本(約1600字)

```markdown
# 巨大なstateをやめた日

「保存」ボタンが、文字を打つたびに2秒遅れて反応しました。原因探しに午後をまるごと使い、最初はサーバーを疑っていた自分が恥ずかしくなりました。

## 最初はすっきり見えていた

3か月前、設定画面の入力欄は4つだけでした。名前、メール、タイムゾーン、言語設定の4つを、私は1つのグローバルなstateにまとめました。

3階層下のコンポーネントへpropsをバケツリレーしたくなかったからです。この近道は驚くほどうまく動き、当時の私は賢い選択をしたと思っていました。

機能追加のたびに、新しい項目を同じ場所へ足していきました。設定画面のデータなのだから、同じ箱に入れて当然だと考えたのです。

コードレビューでも誰も止めませんでした。テスト用の小さなアカウントでは1ミリ秒もかからず動いたからです。その軽さが、2か月間の油断を生みました。

8週目には入力欄が40個に増え、日付ピッカーが3つとリアルタイムのプレビューも付きました。異変に気づいたのは、QAから画面録画が届いたときです。1文字打つたびにカーソルが固まり、画面に文字が出るまで2秒待たされました。

## 2時間、見当違いの場所を探した

私が最初に開いたのは、ブラウザのNetworkタブでした。重いAPIがあるに違いないと決めつけていたのです。

しかし、すべての通信は80ミリ秒以内で返っており、500エラーも1件もありませんでした。バックエンド担当にも確認しましたが、データベースのロックも起きていません。一番重い検索でも15ミリ秒で終わっていました。

次にブラウザのメモリ不足を疑い、拡張機能を全部オフにしました。キャッシュを消して別ブラウザでも試しましたが、それでも「保存」ボタンの重さは変わりませんでした。

そのあいだ、ユーザーからの問い合わせも2件増えました。原因が見えないまま時間が過ぎ、焦りだけが大きくなりました。

夕方4時になって、ようやくReact DevToolsのProfilerを開きました。名前欄に1文字だけ打って計測すると、画面の40個の入力欄がすべて真っ赤に光りました。名前を1文字直しただけで、プレビューも3つの日付ピッカーも最初から計算し直していたのです。

## フォームごとに分け直した手順

エディタを閉じ、どの入力欄がどの欄と連携する必要があるのかを紙に書き出しました。すると、ほとんどの項目は互いに独立していました。アカウント情報を読む必要があったのは、権限スイッチの2か所だけです。

私は巨大な1つの箱を壊し、stateをフォームごとのコンポーネントへ降ろしました。アプリ全体で共有するログイン情報と言語設定だけは、元のグローバルな場所に残しました。プレビュー欄も、いま開いているフォームだけを読むように直しました。

作業には半日かかりましたが、大半は不要なフックを消す時間でした。ブラウザに保存中の下書きが壊れないよう、項目名はそのまま保ちました。直後に同じ1文字入力をProfilerで測ると、描画時間は1800ミリ秒から12ミリ秒まで落ちました。

## まだすっきりしない部分

この変更で遅延は消えましたが、どんな画面にも効く万能薬ではありません。別々のタブにある2つの項目を送信前に突き合わせるときは、親コンポーネントに小さな橋渡しを書く必要があります。

この橋渡しは少し泥臭く、元の箱に戻さずにすっきり書く方法はまだ見つかっていません。独立したフォームが20個並ぶ画面なら、stateを分けるのが一番の近道です。逆に、画面全体が1枚の表計算シートのように連動するなら、まとめて持つ意味があります。

## 誰が必要とするかで決める

私の失敗は、選んだライブラリとは関係ありませんでした。「どこに置けば自分が楽か」を基準にして、「誰が本当にこのデータを読むのか」を考えなかったことが原因です。

今日、1つだけ試してみてください。いま触っているプロジェクトを開き、グローバルなstateに入っている項目を数えてみます。1つの画面でしか使わない項目が5つを超えていたら、ボタンが重くなる前に分け始めどきです。
```
