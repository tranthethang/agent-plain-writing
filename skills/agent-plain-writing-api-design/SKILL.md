# Plain writing

Works in Vietnamese (`vi`), English (`en`) and Japanese (`ja`). This skill handles one document type and uses one of two voice families: `plain` or `creative`.

## Who owns what

Each rule has one owner. Read a rule in its owner file, not in a copy.

| Owner | Owns |
|---|---|
| This file, from "Workflow" to "Extend the skill" | The workflow and the core rules that hold for every type and every language |
| The voice family and type sections at the end of this file | Everything that depends on the type: voice, structure, length policy, sentence rhythm, and the kinds of phrases to ban |
| `languages/<lang>/` | Everything that depends on the language: the unit, numeric limits (`profile.json`), the actual banned phrases (`banned.txt`, `banned-guide.md`), grammar traps, pronoun and level words, terms (`terms.txt`), and examples |

**When two owners disagree:**

- On limits and structure, the type section wins over the core rules.
- On words and grammar, `languages/<lang>/` wins over the type section.
- On how much a text may add beyond the source (reasoning, reactions, inner thoughts), the voice family section and the type section win over the core rules. The facts in core rule 5 never change.
- Every limit that has a key in `profile.json` comes from `profile.json`. No other file repeats it.
- `limits` in `PLAIN-WRITING.md` override `profile.json` for that project. The checker warns when a project limit is above 1.5 times the profile value.

## Workflow

0. **Check for `PLAIN-WRITING.md`** in the project root (template: `templates/PLAIN-WRITING.example.md`). If `PLAIN-WRITING.md` exists, read it and let it win on voice and terms. Use `default_lang` and `default_type` to skip the questions in steps 1 and 2.
1. **Pick the output language** (`vi`, `en` or `ja`). It is the language of the text you produce, not the language of the prompt. A Vietnamese brief that asks for a Japanese manual means `ja`. If unclear, ask one question. Then read `languages/<lang>/profile.json` (the limits for your type) and `languages/<lang>/profile.md`.
2. **Read the type files.** This skill handles one document type. Its voice and structure are in the type section at the end of this file. Read `languages/<lang>/examples/api-design.md`. Also read `languages/<lang>/banned-guide.md`. It is the banned list for the agent. `banned.txt` is the checker's machine list; do not read it. Read `languages/<lang>/terms.txt` only when the type is `user-guide` or `--non-tech` applies. Read only these.
3. **Know the reader**: who they are, what they already know, what they must do after reading. If missing, ask one question. If you cannot ask, state your assumption outside the document (or mark `TBD-n` inline in specs).
4. **Outline** (one line per idea) for any text longer than about 400 words. Write only ideas that are in the outline. In the `creative` family, the outline fixes the scenes, not every sentence.
5. **Draft** with the core rules and the type's voice, structure and rhythm. Write normal paragraphs—never put every sentence on its own line.
6. **Edit** in a separate pass: cut, run the checklist, run the script. Fix until clean. When Python cannot run, apply the final checklist by hand and say in the report that the script did not run.
7. **Report** two things outside the generated text: the result, and what you had to guess. Never prepend or append `Result:`, `Guesses:`, or `**推測したこと:**` lines inside the document. Send the report as a second message when you can. Otherwise end the document, add one line `<!-- report -->`, then the report, and keep it out of the file that the checker reads. When you guessed nothing and added nothing, write no report and no marker. Never write a report that only says so, such as "I did not add facts beyond the brief." In specs, mark missing details inline with `TBD-n`. The script flags those labels (see "Report labels" in `banned-guide.md`) on any line outside code blocks.

Draft and edit are two passes. Do not try to get it right in the first pass.

## Core rules (both families, all languages)

These rules hold for every document type:

| # | Rule | Limit |
|---|---|---|
| 1 | One idea per sentence | In `plain`, two subordinate clauses means split. In `creative`, the type file sets sentence rhythm |
| 2 | Concrete verbs, active voice | "send", not "perform the sending of" |
| 3 | Banned phrases | Zero hits from `banned-guide.md` (the all-types section plus the section for the type) |
| 4 | Opening and closing | Opening: at most 2 sentences, straight to the point. No recap, no empty thanks |
| 5 | No invention | Add no number, event, person, place, technical spec, or outcome that is not in the source. Do not place two numbers with different units or time periods next to each other as a comparison; keep both numbers and narrow the claim to what they support. How much else a text may add (reasoning, reactions, inner thoughts) is set by its voice family |
| 6 | Consistency | One concept, one name. One register for the whole text |

## When the reader is outside the field

Common failure: the AI "translates" every technical detail into plain words. The result is three times longer and still unclear. Do the opposite:

1. Pick **at most 3 ideas** the reader needs.
2. For each idea, say **what the reader gets or can do**. Drop the internal mechanism.
3. Test each sentence: if you delete it, will the reader fail at something or misunderstand something? If not, delete it.

## Cutting order for long drafts

1. Sentences that repeat an earlier idea.
2. Sentences that explain internal mechanism.
3. The second and later examples.
4. Adjectives and adverbs.
5. Empty opening and closing.

For `tech-blog` and `essay`, keep human context, reasoning, and tension instead of cutting down to a bare fact list. In `essay`, also keep the narrator's inner thoughts and the sensory detail each scene needs.

## When editing existing text

- Keep meaning, proper names, numbers, paths and code unchanged.
- Add no new information. List ambiguous spots at the end so the author can decide.
- Give a table "original → revised → reason" if the user wants to learn from the edit.

## Final checklist

- [ ] The script reports no violations.
- [ ] One idea per paragraph, one idea per sentence.
- [ ] No banned phrase from `banned-guide.md`. No empty adjective.
- [ ] Jargon is within the limit. Each term is explained or replaced.
- [ ] The type section's checklist passes.
- [ ] Every number, event and outcome appears in the user's source. In `essay`, every inner thought that the brief does not give is reported outside the text.
- [ ] Register is consistent.
- [ ] Guesses are reported outside the generated document (or marked `TBD-n` inline in specs).

## Voice family

Numeric limits are per language and type. They live only in `languages/<lang>/profile.json`. The type section may relax or tighten a rule. See "Who owns what" for which part wins.

### `plain` (`tech-blog`, `api-design`, `user-guide`, `common`)

One voice: **short, concrete, understood on first read.**

- **Sentence length**: `sentence` in `profile.json`.
- **Paragraph length**: `paragraph` in `profile.json`, one idea.
- **Jargon (reader outside the field)**: `terms` or `non_tech_terms` in `profile.json`. Explain each term in one sentence, or replace it with an everyday word.
- **Examples and metaphors**: One example or story per section, and a section is one main point.
- **Evaluative adjectives** ("great", "powerful", "beautiful"): Replace with a number from the source or a visible detail. If the source has no number, add none.
- **Length**: `length` in `profile.json` is a ceiling, under the type's length policy. The checker warns only above it; a shorter text is fine. Never pad to reach it. Never more than 10% over.
- **Nothing added beyond the source**: keep human context, reasoning, and reactions grounded in the brief. In specs and guides, write `TBD-n <specific question>` or ask.

# API design

Use when you write the design of one API endpoint: purpose, fields, processing and errors. Reader: developers and QA.

## Overrides to the core rules

- Sentence limit is a little looser (see profile).
- Jargon is allowed without limit, but **one concept gets one name**.
- No long prose. Use tables, bullets and numbered steps.
- **Use the fixed template below.** Do not add sections, do not remove sections, do not reorder them.

## Principles

1. **The template owns the structure.** Write `TBD-n` (for example `TBD-1`, `TBD-2`) inline in a section or cell only for an open fact that the brief names, or for a fact without which a developer cannot implement the endpoint. Leave out a slot that the brief does not mention and that does not block implementation. A `TBD-n` is allowed when two rules in the brief conflict, or when a brief rule lacks its input (for example, `slug` comes from `title`, and `title` is optional, so a request may have no `title`). Do not open a `TBD-n` for a case that no brief rule touches. A `TBD-n` may ask for the error of a constraint that the brief states when the brief gives no code for its failure. A `TBD-n` asks for the missing decision (for example, the error when `date` is missing), not for a fact that a stated rule already implies. A bare `TBD` is not allowed. Each `TBD-n` matches one question under Open items, and each question under Open items has its `TBD-n` inline in the section or cell it blocks. Two `TBD-n` must not ask the same question.
2. **One owner for each fact.** Identity owns every role rule, including a role rule on a field value (for example, only one role may set a field to a given value). Processing does not restate it. Errors are written in the Errors table only. Other sections point to them and do not repeat them. Processing lists no validation check and no role check: each check is one row in Errors (condition, HTTP status, code).
3. **Never guess a number, field type, required flag, or component.** Timeout, limit, size, type, required rule: write it if the source has it. A field type is known, not guessed, when any of these four sources gives it: the brief, the glossary, a list of allowed values (an enum of strings), or a list of ids that the glossary calls integers. A field counts as a `string` when its glossary entry describes text: a title, a body, a name, or a part of a URL. Write a known type directly in the table and do not open a `TBD-n` for it. When the source lacks a fact, write `TBD-n` only if the brief names the gap or the developer cannot implement without it; otherwise leave it out.
4. **Name the actor.** "The system checks...", "The client sends...". Avoid the passive voice.
5. **Use requirement words consistently** (RFC 2119 style). One word per level, the same all through the document. The words for each language are in `profile.md`:
   - must: mandatory
   - must not: forbidden
   - should: recommended
   - may: optional
6. **Condition → result** is written "When <condition>, the system must <action>."
7. **Every error has three parts**: the condition, the HTTP status, the error code. Every validation check and every role check is one row in Errors. The Errors table owns the HTTP status and the condition. When the code is an open fact, mark it `TBD-n`. No sentence only points to the Errors table.
8. **No vague words**: no word that leaves a condition, an amount or a speed open. The words for each language are in `banned-guide.md`, section "Vague words in API design", with their replacements.
9. **One concept, one name.** Pick "order" and never mix in "purchase" or "request" for the same thing.
10. **No pointer to another API.** Do not write "same as the other endpoints". Write the rule here.

## Template

Write these sections in this order.

1. **Identity.** Method, path, purpose, and every role rule (here only). Add caller and idempotency only when the brief states them or when the developer cannot implement without them.
2. **DTO and field mapping.** Request and response fields in one table with the columns Field, Direction, Type, Required, Constraint, in this order. Direction states whether the field belongs to the request or to the response (labels in `profile.md`). Response fields are rows in the same table, not a line outside it. A response with unknown fields is one row with `TBD-n` as its type. Required uses the labels in `profile.md`, or `TBD-n`. Write a known field type (Principle 3) directly in the table with no `TBD-n`. Use `TBD-n` for a field type only when the type is not known and it blocks implementation. The Constraint column holds input limits only; a default or a generated value lives in Processing (Principle 2). Write `—` in a cell that has no value. Do not leave a cell empty.
3. **Endpoint.** One request example and one success response example with its status. Write the success status here only. An example holds no `TBD-n`. Use only fields whose type the brief or the glossary gives. When no such field is known, leave out that example and write nothing in its place.
4. **Processing.** Number the steps in execution order only when the brief states the order; otherwise list unnumbered rules and mark execution order or error precedence `TBD-n`. Processing holds only behavior that no other section owns: generated values, defaults, the execution-order line and the error-precedence line. It lists no validation check and no role check; those live in Errors (and the role rule in Identity). When the section has nothing else, it holds only the order and precedence line. Skip the Mermaid diagram when the execution order is `TBD-n` or fewer than three nodes carry meaning, and write nothing in its place. Otherwise add one Mermaid sequence diagram or flowchart in a fenced code block using only actors and components named in the brief. Give each rule that has an empty or edge case its own step.
5. **Errors.** One table with condition, HTTP status and code. Errors appear nowhere else.
6. **Side effects.** Audit, events, cache, async jobs. When the brief states no side effect, or the call is read-only, the section text is exactly `None` (the label in `profile.md`), with no sentence around it. Add other effects only when the brief states them or when the developer cannot implement without them. Never repeat the main action of the API.
7. **Open items.** Every `TBD-n` with its question (write each question here once; keep inline cells to `TBD-n`; no duplicate question, see Principle 1). Open items hold spec questions only: do not ask for an example, ask one thing per question (the HTTP status and the code of one error row are one question), and do not ask what the brief already answers.

The template excludes tech stack, convention, error contract, changelog and test links. The project convention lives outside the API file.

## Brief the AI needs

1. The idea of the API: purpose, who calls it, when.
2. Business rules already decided.
3. One fully filled API as a model.
4. The glossary of agreed terms (if any).

If item 1 or 2 is missing, ask. Do not infer business rules.
